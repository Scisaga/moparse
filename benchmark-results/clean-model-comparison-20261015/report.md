## 新版优化与调用配置

[PaddleOCR-VL 1.6 官方介绍](https://huggingface.co/PaddlePaddle/PaddleOCR-VL-1.6)的重点包括弱区域数据与监督、后训练及强化学习，以及表格等任务改进。本轮在相同整页输入、布局、提示和生成预算下看到真实金额恢复、原始核心数值 206→208、两处旧生成循环结束。调用方式也有影响：原件正向的第 56 页被方向分类器额外转了 270°，该调用产生冲突跨度；关闭额外方向后的结构有效。方向 ON 是本轮显式控制因子，Paddle 官方默认是 OFF；额外方向预处理需要按原件类别验证。

[TableFormer V2](https://huggingface.co/docling-project/TableFormerV2)是强调推理效率的预览结构模型，V1 仍为默认。本轮确认缓存已启用；同一新版 Docling、默认 PDF 后端、matching=True、四线程 CPU 下，完整 46 页转换中位数 **97.74→84.84 秒，缩短 13.2%**。本次样本及受测集成中的质量尚不足以全面替代 V1，且后端影响明显：V2 的 402 项原值行确认数由默认后端的 155 提高到 PyPdfium 后端的 217，后者是更好的 V2 质量配置。相同新版库、matching=True 下，V1／V2 在 PyPdfium 后端分别为 384／217，在默认后端分别为 377／155；后端与权重的配对结果均保留。V2／PyPdfium 没有在本轮另做串行计时。不能把某个集成结果直接归因于权重本身。

2026-10-17 对官方源码及原始预测的复核进一步确认：

- V1 的 matching=True 调用官方 `MatchingPostProcessor`，包含列对齐、文字重新归属、框调整及遗漏文字恢复；V2 从 OTSL 和预测框直接建格再按重叠取字，两者参数同名但实现不同。
- 安装的 V2 适配器、V1 后处理和预测代码与对应官方标签源码字节一致。这是官方集成差异，不能将所有差距解释为 MosaicParse 旧修复或纯模型权重差异。
- 原件第 56 页的官方 CPU 单页诊断复现了先前完整 134 页结果。V2 生成 114 个 token 并以 EOS 结束，未达到 512 上限；原始预测框已漏掉 `1,008,421,848.10` 的末位 0，最终把它放到下一行。V1 在官方后处理前已完整覆盖该金额。这一具体错误始于原始结构预测。

尚未逐一解释全部失败项，不能宣布 V2 在所有 PDF 上纯模型精度更差。此次单页诊断不是新的全语料评分或完整 PDF 验收。原始框、token、脚本及采集限制另存于 `followup/20261017/tableformer-v2/`。

Docling 的库版本和 PDF 后端也有独立影响。固定 V1／matching=False／PyPdfium 时，新旧库均为 398／332；切到新版默认 Threaded 后端则为 264／137。源码及原件已定位一个具体原因：其矩形取字要求覆盖文本行超过 50%，第 2 页某金额实际覆盖为 44.26%，因此返回空文字。这个变化发生在取字后端，和更换结构模型权重是不同因素。

[GLM-OCR SDK 0.1.5](https://github.com/zai-org/GLM-OCR/releases/tag/v0.1.5)是管线与配置等更新，本轮识别权重固定。SDK 请求前加入共同的官方方向分类器后，核心核对从 202／209 提高到 209／209，属于调用栈的实际改善。
