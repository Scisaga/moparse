# Native worker 内存快速只读诊断

当前没有 OOM、重启或请求失败证据，不建议因本次触顶立即停测、扩内存或改变冻结组合。已确认发生容器上限压力和少量交换；它是真实资源成本，不能写成“8GiB 内完全无压力”。这次只读无法区分全部 live ONNX buffer 与 allocator 空闲页，不足以宣布内存泄漏。

未运行解析、模型或 GPU 请求，未注入 Python/GC、malloc_trim、信号，未改环境、源码或容器。

## 实测

容器 `moparse-native-worker`：8GiB memory 上限、16GiB memory+swap 上限，RestartCount=0、OOMKilled=false。memory.peak=8589934592 bytes，events.max=507，oom/oom_kill=0。

当前 memory≈8,003,026,944 bytes（7.45GiB）、swap≈167,014,400 bytes（159MiB）。约1分钟间隔的两个快照中 current、swap、max 事件数和 PSI total 都基本/完全不变；PSI avg10/60/300=0。因此触顶导致过回收/交换，观察窗口内没有持续压力增长或内存停顿。events.max 不是 OOM 计数。

uvicorn 主进程 RSS≈7.31GiB、Anon≈7.25GiB，4个子进程总计约285MiB；主进程51线程。cgroup file 仅约360KiB，shmem约4KiB，说明不是 Linux 可丢弃文件缓存，也不是遗留的 GB 级 shared pixel buffer。主进程有大量约64MiB匿名映射和若干260–520MiB映射；与多线程 glibc arenas/ONNX 会话高水位相容，但 smaps 不能证明每块的分配者或空闲比例。

## 已安装官方路径核对

- 自有 `native_worker/server.py:146–190` 每请求持有本地 `result` 和导出 JSON，没有跨作业结果全局列表；只用单文档锁。整份 typed result 与 JSON 导出会在当前请求短暂共存，响应编码还有副本，所以整文档峰值仍高于单个处理窗口。
- MinerU `parser/__init__.py:28–41` 每调用新建 parser；`mineru_parser.py:67–88` 解析中间数据为局部变量，没有 last-result 字段。
- `backend/analysis/pdf/pipeline.py:72–83` 文档 finally 关闭 PDF，release_document 后请求 clean_memory，再调用 trim_process_heap。CPU clean_memory 在 `model/runtime/memory.py:59–64` 执行官方 gc.collect。我们未主动调用它。
- `backend/analysis/pdf/window.py:333–346,614–618` 每窗口 finally 显式关闭 PIL、清空 images/NumPy/window_pages/text/vector geometry、关闭 snapshot。64页窗口是当前实际设置；高分辨率页可能同时存在 PIL、NumPy、OCR/布局中间量，足以形成较高暂态峰值。
- DocVortex `_document.py:463–481` 关闭 PDFium 和 render session；`render_session.py:556–610` 要求子进程确认释放输入，清 shared pixels、临时目录和 `_pdf_bytes`，缓存复用 worker 进程而非保留旧 PDF 输入。
- `model/runtime/hybrid.py:191–245,338–361,387–446` 有按固定 backend/device/config 缓存的 ONNX 本地模型和惰性属性；会话保留跨作业，属于官方复用设计。通用 ONNX session (`runtime/onnx.py:46–52`) 没有显式禁用 CPU arena/memory pattern；这类会话和 glibc 的高水位保留是合理候选，尚未测定各自占比。
- `model/vlm/runtime.py:35–115` 缓存 HTTP predictor，当前固定模型/URL/参数形成固定 key；`async_runtime.py:144–152` 完成后从 `_submissions` discard，没有看到按文档不断增长的已完成请求集合。

重要：官方 `trim_process_heap` **默认不开启**。`runtime/memory.py:32–44` 仅在 `MINERU_MALLOC_TRIM=1/true/...` 时才执行 libc malloc_trim。当前仅白名单读取进程环境确认该项未设，`MALLOC_ARENA_MAX` 也未设。故不能因为 pipeline 有 trim 调用就声称已经把空闲 native 堆归还 OS。ONNX 会话仍持有的 arena 也不会仅靠 glibc trim 自动释放。

## 后续最小实验建议

本轮39+7继续原配置，记录 current/peak/swap/events/PSI；若实际 oom/restart/请求失败或压力持续增长，再按证据处理。完成后单独测试官方 `MINERU_MALLOC_TRIM=1` 的 idle RSS/交换量/推理耗时变化，保持模型和内容不变；必要时再独立比较更小 processing window。不能在同一轮中途开启，也不能把这两个设置未经完整回归就称为质量无影响。若要精确证明泄漏或定位 C++ arena，需要另外授权的长期重复作业和分配器测量；当前只读证据不支持直接归因 V3 marker 修复或自动扩容。

`snapshot.json` 保存精确 cgroup/status/smaps、白名单环境和11个已安装 upstream 源文件 SHA；不包含容器密钥。正式冻结源码未改。
