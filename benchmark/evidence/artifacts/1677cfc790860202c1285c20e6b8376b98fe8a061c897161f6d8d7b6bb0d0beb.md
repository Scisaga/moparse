# V4：控制 CPU 公式识别和页面工作集

V3 的完整504页质量检查已通过，随后 NIST25 的18个原生页完成 VLM 阶段，在 CPU MFR 的26公式任务完成8项后 native worker 重启。root已捕获 kernel `CONSTRAINT_MEMCG` 对所属cgroup的 uvicorn 进程 OOM kill，以及 Docker oom/die137/start 事件。重启后的 `OOMKilled=false` 和清零事件不能否定这次历史 OOM。V3结果、冻结和首个失败保留，V4是独立资源方法，尚未声称通过真实HTTP。

唯一算法补丁在固定 MinerU4.0.12 的 CPU MFR 批次切分：`PPFormulaNetPlusMONNX._infer_batch` 原 cap=8、pipeline请求32，现在允许明确的 `MOPARSE_CPU_MFR_BATCH_SIZE` 将 cap 降为1–8。未设时仍为8，非法值显式失败；正式镜像/Compose显式1。所有公式仍进入原有面积排序、预处理、相同ONNX权重、相同解码及原位置回填；不关闭公式、不截断数量、不按PDF/页号/词汇分流，不改变表格、表头、期间或来源映射。

另两项是官方已有资源控制，镜像与root维护的Compose均显式设置：

| 控制 | SDK读取位置 | SDK未设默认 | V4显式值 |
| --- | --- | --- | --- |
| MOPARSE_CPU_MFR_BATCH_SIZE | 本次锁定补丁 `_cpu_batch_limit` / `_infer_batch` | 8 | 1 |
| MINERU_PROCESSING_WINDOW_SIZE | `backend/analysis/pdf/window.py:_configured_window_size` | 64页 | 8页 |
| MINERU_MALLOC_TRIM | `model/runtime/memory.py:trim_process_heap` | 关闭 | 开启 |

官方窗口关闭后及整文档 finally 均会调用受开关控制的 trim。trim不等于释放所有ONNX持有的arena，微批1也不是任意输入下的8GiB保证；必须以失败点及全量真实HTTP实测确认。容器内存上限仍8GiB、单文档锁与VLM并发2不变。未切换GPU/权重/模型版本、384×384 MFR预处理、Tokenizer、公式解码、Docling头核验或GLM路由。

`patch_dependency.py` 对文字方向补丁和新增MFR补丁同时预检版本/原SHA或已补SHA，拒绝漂移后才写入，支持重复应用。启动先核对两份已补源码SHA和合法cap；`/ready` 新增内部 `resource_policy`，报告批次/窗口/trim及MFR源码SHA，旧 `text_matching` 与解析协议保持可用。renderer只新增一处空列表类型注解，行为不改。
