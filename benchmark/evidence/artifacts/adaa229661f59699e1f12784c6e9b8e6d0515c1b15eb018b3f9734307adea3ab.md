## 调用和配置核对

- 固定模型 MinerU2.5-Pro-2605-1.2B，revision `08aaea840498d49ce16247b6263196cf02814885`；MinerU4.0.12 Advanced(xhigh)+TXT。
- worker SDK2.0.7；provider vLLM0.19.1。官方 V1 processor 源码明确支持 vLLM>=0.19.1,<0.29.0，实际接口 extra_args/output-token 状态传递符合其实现。
- GPU真实命令注册 `mineru_vl_utils:MinerULogitsProcessor`；half、eager、8192 context、max_sequences2、KV128MiB、batched_tokens2048。
- 抓包中的任务为官方 `\nLayout Detection:` / `\nTable Recognition:`。table使用 temperature0、top_p0.01、top_k1、presence1、frequency0.005、repetition1、no_repeat_ngram_size100、skip_special_tokens=false，与安装的官方 SDK 默认值一致。没有自定义金融词提示或期间补写。
- 未传显式 max_tokens，服务文本 context8192；本例2595输出tokens正常 stop，不应把加长 context 当修复。
- 本机2080Ti计算能力7.5不能原生BF16；FP16与原模型config BF16存在数值路径差异，但不能在本次未做消融时认定为根因，也不能承诺在现卡改成BF16。
- `native_worker/server.py:167` 显式 `image_analysis=False`，官方 parser/runtime 默认 True。这是当前组合与完整图像分析模式的实质差别，应登记验证。但 SDK 该开关只控制已经标为 image/chart 的块是否分析；本块已被布局阶段标成 table，仅开 True 没有重新分类这个框的机制，不能保证修复。
- native 源字符轴向匹配和 CPU MFR 微批 patch 不改变 VLM 请求、模板、图像或采样；重复已经在其前的原始模型响应中。

## 官方 no_repeat100 与合法重复存在冲突

`mineru_vl_utils/logits_processor/vllm_v1_no_repeat_ngram.py:61–89` 对全部输出 token 建立 n-gram，无 OTSL 结构 token 豁免。tokenizer 中 `<lcel>/<ecel>/<fcel>/<ucel>/<xcel>/<nl>` 各为一个独立 token。

本次原始响应的第1行只有 FY23、FY24 两个年份，FY24后连续100个 `<lcel>`。按官方算法逐token CPU复演：第113个下一token禁止再出 `<lcel>`，实际改出 `<nl>`；第219个同时禁 `<lcel>` 和 `<nl>`，实际出 `<ecel>`；第319个又禁 `<ecel>`，实际换行。原输出不存在违反该约束的100-token重复。这说明防重复约束在起作用，但它将已有错误扩张导向了另一种结构，并没有保证源图一致。

另一方面，原件可见月序 `M J J A S O N D J F M A` 循环6次。对这个正常月度行进行仅CPU、反事实的逐格 OTSL 编码，在第124个输出 token 开始全局 no_repeat100 就会禁止源中正确重复的 J 和后续 `<fcel>`。这是表达能力冲突的确定反例，不是第三次模型调用，也不是对结果补写。原始错误早在达到100次限制前就已出现，因此不能从这个反例推断关约束即可修复模型。

没有足够证据推荐直接降低 ngram、增加惩罚或回退100列硬上限：这些办法会影响合法重复月行、金额、表头及已有 IRS202列合法表。
